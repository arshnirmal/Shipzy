# Database Folder Structure

## Overview

This folder contains all database-related code and SQL files for the Shipzy backend.

**⚠️ IMPORTANT**: We use **Drizzle Kit** to generate SQL migrations from TypeScript schema definitions. The `schema/` folder is the **single source of truth**.

## Folder Structure

### 📁 `schema/` (TypeScript - Drizzle ORM) ⭐ SINGLE SOURCE OF TRUTH
**Purpose**: Drizzle ORM TypeScript schema definitions used by application code.

**Contents**:
- `index.ts` - Main schema export
- `public.ts` - Public schema tables + native PG enums (delivery_types, status/role enums, etc.)
- `users.ts` - User-related tables (profiles, addresses, auth_sessions)
- `orders.ts` - Order-related tables (requests, courier_assignments)
- `logistics.ts` - Logistics tables (courier_status, courier_vehicles, locations)
- `payments.ts` - Payment tables (transactions, refunds)
- `tracking.ts` - Tracking tables (events)
- `ratings.ts` - Ratings tables (driver_ratings)
- `notifications.ts` - Notification tables (queue, fcm_tokens)
- `relations.ts` - Drizzle relations definitions
- `types.ts` - TypeScript types for JSONB structures

**Used by**: Repository files, Drizzle ORM queries

**Example**:
```typescript
import { userProfiles } from "../../database/schema/users.js";
import { orderRequests } from "../../database/schema/orders.js";
```

---

### 📁 `migrations/` (SQL - Auto-generated Migrations)
**Purpose**: SQL migration files **automatically generated** from TypeScript schema by Drizzle Kit.

**Contents**:
- Auto-generated migration files (e.g., `0000_initial.sql`, `0001_add_column.sql`)
- Generated by running: `npm run db:generate`
- **Git-tracked** - these files are committed to version control

**Used by**: 
- `scripts/db-deploy.ts` - Deployment script executes these migrations

**⚠️ DEPRECATED**: The `schemas/` folder is deprecated. Use Drizzle migrations instead.

### 📁 `seeds/` (SQL - Reference data)
**Purpose**: Idempotent `INSERT` scripts for lookup tables.

**Contents**:
- `master-data.sql` — reference rows (`delivery_types`, `weight_tiers`, `payments.payment_methods`, capabilities, labels, `pricing_config`, etc.). Applied automatically at the end of `db:deploy`.

**Used by**: `scripts/db-deploy.ts`, `scripts/seed-master.ts`, `tests/database.js` (`runSeeds`)

### 📄 `setup.sql` (SQL - One-time Setup)
**Purpose**: Extensions and schema creation (run once per database).

**Contents**:
- PostGIS extensions
- Schema creation (users, orders, logistics, etc.)

**Used by**: 
- `scripts/db-deploy.ts` - Runs once on initial setup

---

### 📁 `queries/` (TypeScript - Raw SQL Queries)
**Purpose**: Raw SQL query strings used by repositories.

**Contents**:
- `auth.queries.ts` - Authentication queries
- `users.queries.ts` - User management queries
- `orders.queries.ts` - Order queries (optimized for JSONB)
- `drivers.queries.ts` - Driver/courier queries
- `ratings.queries.ts` - Rating queries
- `static.queries.ts` - Static data queries
- `sessions.queries.ts` - Session queries
- `payments.queries.ts` - Payment queries
- `tracking.queries.ts` - Tracking queries
- `notifications.queries.ts` - Notification queries

**Used by**: Repository files for complex queries that can't be done with Drizzle

---

### 📁 `functions/` (SQL - Stored Functions)
**Purpose**: PostgreSQL stored functions (PL/pgSQL) for complex business logic.

**Contents**:
- `auth.sql` - Authentication functions (send_otp, verify_otp_and_create_user)
- `orders.sql` - Order functions (calculate_fare, create_order_with_locations, cancel_order_with_refund)
- `logistics.sql` - Logistics functions (find_nearby_couriers)
- `payments.sql` - Payment functions
- `tracking.sql` - Tracking functions

**Used by**: Repository files via raw SQL calls

---

### 📁 `utils/` (TypeScript - Database Utilities)
**Purpose**: Utility functions for database operations.

**Contents**:
- `executeRaw.ts` - Type-safe raw SQL query wrapper
- `postgis.ts` - PostGIS helper functions

---

### 📄 Root Files
- `db.ts` - Raw PostgreSQL connection pool
- `drizzle.ts` - Drizzle ORM instance
- `drizzle.config.ts` - Drizzle Kit configuration
- `transaction.ts` - Transaction helpers (Drizzle and raw SQL)

---

## Migration Workflow

### 1. Edit TypeScript Schema
Edit files in `schema/` (e.g., `schema/orders.ts`)

### 2. Generate Migration
```bash
npm run db:generate
```
This generates SQL migration files in `migrations/`

### 3. Deploy
```bash
npm run db:deploy
```
This runs `setup.sql` (once), pending migrations from `migrations/`, refreshes `functions/*.sql`, then applies `seeds/master-data.sql` (idempotent reference data).

### 4. Optional: API-driven seed
`pnpm run db:seed` calls the HTTP API (`seed-api.ts`) and expects master data to exist first (via `db:deploy` or `db:seed:master`).

## Key Differences: `schema/` vs `migrations/`

| Aspect | `schema/` (TypeScript) | `migrations/` (SQL) |
|--------|------------------------|---------------------|
| **Language** | TypeScript | SQL |
| **Purpose** | Source of truth (edit this) | Generated migrations |
| **Used by** | Application code + Drizzle Kit | Deployment scripts |
| **Format** | `.ts` files | `.sql` files |
| **When executed** | At runtime (imported) | At deployment (psql) |
| **Contains** | Drizzle table definitions | Generated CREATE/ALTER statements |
| **Edit?** | ✅ YES - This is what you edit | ❌ NO - Auto-generated |

## Best Practices

1. **Schema Changes**: 
   - ✅ **ONLY edit** `schema/` (TypeScript) - this is the single source of truth
   - ❌ **Don't edit** `migrations/` directly - regenerate instead
   - Run `npm run db:generate` after schema changes

2. **Migrations**:
   - Generated automatically from TypeScript schema
   - Review generated SQL before deploying
   - Commit migrations to git (they're part of codebase)

3. **Queries**:
   - Use Drizzle ORM for simple CRUD operations
   - Use raw SQL in `queries/` for complex queries with CTEs, JSON aggregation, PostGIS

4. **Functions**:
   - Keep stored functions in `functions/` for complex business logic
   - Use `CREATE OR REPLACE` syntax for idempotent deployment

## Deployment Flow

```
1. Edit TypeScript Schema (schema/*.ts)
2. Generate Migration (pnpm run db:generate) → Creates migrations/*.sql
3. Deploy (pnpm run db:deploy) → setup.sql + migrations/*.sql + functions/*.sql + seeds/master-data.sql
4. Optional: pnpm run db:seed → HTTP API seed (seed-api.ts)
5. TypeScript schemas imported at runtime by application code
```

## Commands

- `pnpm run db:generate` - Generate SQL migrations from TypeScript schema
- `pnpm run db:deploy` - Deploy setup, migrations, functions, and master reference data
- `pnpm run db:seed:master` - Apply `seeds/master-data.sql` only (e.g. if DB existed before master seed was added)
- `pnpm run db:seed` - Seed via API (`seed-api.ts`)

## Verification After Init (Docker)

After `docker compose up` with a fresh volume, the **postgres** container runs `db-init.sh`, which:

| Step | Created | Source |
|------|---------|--------|
| 1 | Extensions: postgis, btree_gist, uuid-ossp, pg_stat_statements | `setup.sql` |
| 2 | Schemas: users, logistics, orders, payments, tracking, notifications | `setup.sql` |
| 3 | Stored functions (auth, logistics, orders, payments, tracking) | `functions/*.sql` |
| 4 | Role `shipzy_user` and grants | `db-init.sh` |

**Tables** are **not** created by init. They come from Drizzle migrations. Ensure you have migration files and deploy:

1. Generate migrations (if none): `pnpm run db:generate`
2. Deploy (from host or backend container): `pnpm run db:deploy` (also loads `seeds/master-data.sql`)

Static API routes expect reference rows from `master-data.sql`; without deploy’s seed step, `/static/*` responses may be empty.
